# Замеры скорости C++ ядра

Инструмент — `p2pcore_bench` (`cpp/tools/bench.cpp`). Он качает тестовый файл целиком при разных
размерах чанка и окнах запросов (`max_inflight`) и печатает таблицу МиБ/с (медиана повторов).
Время считается от `request_chunks` до последнего `CHUNK_RECEIVED`: в него входят сеть, CRC32C и
запись `.part` на диск (обычно в кэш ОС).

## Сборка

```
cmake -S . -B build/bench -G Ninja -DCMAKE_BUILD_TYPE=Release -DP2P_BUILD_TESTS=ON
cmake --build build/bench --target p2pcore_bench
```

Мерить только в **Release**: в Debug ядро в разы медленнее, и цифры ничего не говорят.

## Режимы

**`loop`** — оба движка в одном процессе, через 127.0.0.1. Сети нет, поэтому это предел самого
ядра (CPU, копирование, диск), а не скорость LAN:

```
build/bench/p2pcore_bench loop --csv loop.csv
```

**`serve` / `fetch`** — между двумя компьютерами. На раздающем:

```
build/bench/p2pcore_bench serve --port 50600
```

Он напечатает команду для второго компьютера:

```
build/bench/p2pcore_bench fetch 192.168.1.10:50600 --csv lan.csv
```

`--size` и `--chunks` у `serve` и `fetch` должны совпадать: по ним обе стороны строят одинаковые
`file_id`. Брандмауэр Windows при первом запуске `serve` спросит разрешение на входящие
подключения — разрешить для частной сети. `serve` останавливается по Enter.

Опции: `--size MiB` (256), `--chunks 64,256,1024,4096` (КиБ), `--windows 1,2,4,8,16`,
`--repeat 3`, `--csv FILE` (дописывает все замеры, по строке на повтор — удобно строить график).
Полная матрица по умолчанию — 20 комбинаций × 3 повтора × 256 МиБ: на loopback около минуты,
по гигабитной сети около восьми минут (для пробы: `--size 64 --repeat 1`).

## Результаты

### loopback, 2026-11-10

AMD Ryzen 5 5600X, 32 ГБ, Windows 10, MinGW GCC 15.2, Release; 256 МиБ, медиана из 3, МиБ/с:

| чанк \ max_inflight |   1 |   2 |   4 |   8 |  16 |
| ------------------- | --: | --: | --: | --: | --: |
| 64 КиБ              | 184 | 351 | 369 | 364 | 370 |
| 256 КиБ             | 211 | 394 | 394 | 396 | 392 |
| 1 МиБ               | 214 | 402 | 402 | 402 | 401 |
| 4 МиБ               | 213 | 386 | 385 | 387 | 382 |

Что видно:

- **Окно 1 вдвое медленнее остальных.** С одним запросом «в полёте» отдающий простаивает, пока
  запрос идёт к нему, а получатель — пока ждёт первый байт ответа. Уже двух запросов хватает,
  чтобы канал не простаивал между чанками (pipelining, ARCHITECTURE.md, контроль потока).
- **Больше 2–4 окно не помогает:** на loopback задержка почти нулевая. По сети с заметным RTT
  нужное окно больше — его покажет замер `fetch`. По умолчанию в ядре `max_inflight = 6`.
- **Размер чанка от 256 КиБ до 1 МиБ — лучший.** 64 КиБ проигрывают ~8 % на накладных расходах
  кадра и запроса на каждый чанк. 4 МиБ чуть хуже 1 МиБ; вероятная причина (не проверялась
  отдельно) — CRC считается отдельным проходом по чанку, и для большого чанка повторное чтение
  реже попадает в кэш процессора.
- Предел ~400 МиБ/с — это ядро на одном io-потоке на этой машине, с запасом выше гигабитной сети
  (~117 МиБ/с), так что по LAN упираемся в сеть, а не в ядро.
