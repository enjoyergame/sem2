# Протокол P2P Share, версия 1

Контракт №1 между пирами. Реализация — `cpp/include/p2pcore/protocol.hpp`, `cpp/src/protocol.cpp`,
`cpp/src/connection.cpp`. Транспорт — TCP; обнаружение пиров (UDP) описано в ARCHITECTURE.md, раздел 3.1.

## 1. Кадр

Каждое сообщение = **заголовок 40 байт** + нагрузка `payload_len` байт. Все числа — **big-endian**.

| Смещение | Размер | Поле             | Описание                                                                        |
| -------: | -----: | ---------------- | ------------------------------------------------------------------------------- |
|        0 |      4 | `magic`          | `0x50325046` (`"P2PF"`) — быстрое отсечение мусора                              |
|        4 |      1 | `version`        | `1`                                                                             |
|        5 |      1 | `type`           | тип сообщения, раздел 2                                                         |
|        6 |      2 | `flags`          | резерв (сжатие/шифрование в будущем)                                            |
|        8 |     16 | `file_id`        | первые 16 байт `file_id` (ARCHITECTURE.md, 2.5); нули для сессионных сообщений |
|       24 |      4 | `chunk_index`    | индекс чанка, `0xFFFFFFFF` если неприменимо                                     |
|       28 |      4 | `payload_len`    | длина нагрузки, не больше `MAX_PAYLOAD` = 16 МиБ                                |
|       32 |      4 | `payload_crc32c` | CRC32C (Castagnoli) нагрузки, 0 при пустой                                      |
|       36 |      4 | `seq`            | номер кадра в соединении (только для отладки)                                   |

Для Python-тестов тот же заголовок: `struct.Struct(">IBBH16sIIII")` (ровно 40 байт).

CRC32C: полином `0x1EDC6F41` (отражённый `0x82F63B78`), начальное значение и финальный XOR
`0xFFFFFFFF`. Проверочное значение: `crc32c(b"123456789") == 0xE3069283`.

### Проверки при приёме заголовка

Строго в таком порядке; первая неудача — разрыв соединения:

1. `magic` ≠ `0x50325046` — это вообще не наш протокол;
2. `version` ≠ 1 — в другой версии поля могут лежать иначе;
3. `payload_len` > 16 МиБ (ровно 16 МиБ допустимо) — защита от мусора;
4. `type` не из таблицы раздела 2.

`flags`: отправитель пишет 0, получатель **игнорирует** (так версия 1 не сломается от новых флагов).
CRC нагрузки проверяется после её чтения; несовпадение у любого кадра, кроме `CHUNK`, — разрыв
(у `CHUNK` — только провал этого чанка, раздел 4).

## 2. Типы сообщений

| Код  | Тип        | `file_id` | `chunk_index` | Нагрузка                                                   |
| ---- | ---------- | :-------: | :-----------: | ---------------------------------------------------------- |
| 0x01 | `HELLO`    |     —     |       —       | `peer_id[16]`, `listen_port u16`, `caps u32`, имя UTF-8 (до 255 байт) |
| 0x02 | `PING`     |     —     |       —       | `timestamp_ns u64` — время отправителя                     |
| 0x03 | `PONG`     |     —     |       —       | эхо нагрузки `PING`                                        |
| 0x0F | `BYE`      |     —     |       —       | `reason u16` (раздел 3)                                    |
| 0x10 | `CONTROL`  |     —     |       —       | непрозрачные байты (UTF-8 JSON, разбирает Python)          |
| 0x20 | `BITFIELD` |     ✓     |       —       | битовая карта: MSB-first, `ceil(n/8)` байт, хвостовые биты 0 |
| 0x21 | `HAVE`     |     ✓     |       ✓       | —                                                          |
| 0x30 | `REQUEST`  |     ✓     |       ✓       | —                                                          |
| 0x31 | `CHUNK`    |     ✓     |       ✓       | данные чанка (последний чанк файла может быть короче)      |
| 0x32 | `REJECT`   |     ✓     |       ✓       | `reason u16` (раздел 3)                                    |
| 0x33 | `CANCEL`   |     ✓     |       ✓       | —                                                          |

Нагрузка неверной длины (`HELLO` короче 22 или длиннее 277 байт, `PING`/`PONG` не 8 байт,
`BYE`/`REJECT` не 2 байта) — нарушение протокола, разрыв.

## 3. Коды причин

`REJECT.reason`:

| Код | Имя            | Когда                                                                       |
| --: | -------------- | --------------------------------------------------------------------------- |
|   1 | `UNKNOWN_FILE` | такого `file_id` у отдающего нет                                            |
|   2 | `NOT_HAVE`     | чанк ещё не проверен (`set_have` не вызван), индекс вне файла, ошибка чтения |
|   3 | `BUSY`         | в очереди отдачи уже 64 чанка                                               |
|   4 | `CANCELLED`    | ответ на `CANCEL` чанка, отдача которого ещё не началась                    |

`BYE.reason`: 1 `NORMAL` (штатное закрытие), 2 `PROTOCOL_ERROR`, 3 `INCOMPATIBLE`
(подключение к самому себе, несовместимая версия), 4 `DUPLICATE` (резерв: дубли соединений решает Python).

## 4. Правила

**Рукопожатие.** Обе стороны сразу после установления TCP отправляют `HELLO`. Первый кадр от
собеседника обязан быть `HELLO`, второй `HELLO` — нарушение. Пока `HELLO` не получен, другие
кадры не обрабатываются. Не пришёл за отведённое время (по умолчанию 10 с у входящего, `timeout_ms`
у исходящего `connect`) — разрыв. Если `peer_id` и `listen_port` собеседника совпадают с нашими,
это подключение к самому себе: `BYE(INCOMPATIBLE)` и закрытие.

**Ровно один ответ на каждый `REQUEST`:** `CHUNK` или `REJECT`. Поэтому запрашивающий всегда знает,
когда освобождается место в окне запросов (`max_inflight`, по умолчанию 6). Повторный `REQUEST`
того же чанка, пока первый ещё «в полёте», не отправляется.

**`CANCEL`.** Если отдача чанка ещё не началась — отдающий снимает его из очереди и отвечает
`REJECT(CANCELLED)`. Если уже началась — `CHUNK` придёт целиком; запрашивающий его дочитывает
и выбрасывает. Отменённые запросы событий в Python не порождают.

**`CHUNK`.** Получатель проверяет, что такой запрос в полёте и `payload_len` равен длине чанка;
иначе — нарушение протокола (незапрошенный `CHUNK`), разрыв. Нагрузка читается слайсами по
64 КиБ и сразу пишется в `.part` по смещению `chunk_index × chunk_size`. CRC не совпал —
провал только этого чанка (`CHUNK_FAILED`, код 4), соединение живёт.

Отдающий считает CRC в два прохода по 64 КиБ: первый проход — CRC для заголовка,
второй — отправка (повторное чтение попадает в кэш ОС). В памяти никогда нет чанка целиком.

**Keepalive.** `PING` раз в 5 с; если 15 с от собеседника не пришло ни одного байта — разрыв.

**Закрытие.** Штатное: `BYE(NORMAL)`, затем закрытие своей половины соединения (FIN) и
дочитывание входа, пока собеседник не закроет свою (так `BYE` не теряется из-за RST).
Собеседник, получив `BYE`, закрывает соединение. Обрыв без `BYE` (ошибка сокета, EOF,
таймаут, нарушение протокола) — у обеих сторон это нештатный разрыв. Все запросы «в полёте»
при любом разрыве считаются проваленными.
